# Jellyfin Thunder Subtitle

为 Jellyfin 影视库自动补全中文外挂字幕，**由 AI 大模型在候选字幕之间择优**。

当迅雷字幕库对同一部影片返回多份中文字幕时，插件会下载全部候选，逐条解码、校验格式，
先扫一遍能自动数出来的毛病（含中文率、未译标注、大段空白、断句过粗），
再把干净的若干份按时间轴对齐后交给大模型横向比较，选出最接近人工翻译的一份，
写成 `<片名>.chi.srt` / `<片名>.chi.ass` 并与视频文件放在同一目录 ——
Jellyfin 会将其识别为**外部字幕**，播放时可直接选择。

面向 Jellyfin **12.2.0**（`targetAbi = 12.2.0.0`，`net10.0`）。

---

## 特色

### AI 大模型择优

同一部影片在迅雷上往往存在十余份中文字幕：人工翻译、AI 机翻，以及同一份字幕的不同转码版本。
**台词多并不代表翻译质量高** —— 双语字幕夹着整行英文，字数天然翻倍；机翻也常常更长，
因为每个语气词都被逐字直译了出来。

因此插件分三步决定用哪一份：

1. **先淘汰有硬伤的**（本地就能数出来，不花 token）：含中文条数不足 90%、
   未译标注超过 20 条、相邻台词间有超过 5 分钟的空白、平均每条台词超过 10 秒。
2. **再排序**：缺陷少的优先 → 条数接近本批中位数的优先 → 名字带「国配 / 官方 / 院线」
   等专业译制标记的微调。**台词字数不参与排序。**
3. **交给 AI 横向比较**：把候选按时间轴对齐成若干连续片段放进同一个请求，
   由模型逐份评分，并引用原句作为证据。

> 实测《加勒比海盗》时，用户手工挑中的国配台本在 8 份候选里拿到最高 **81 分**
> （「多数段落像中文原创台词」），最好的双语版只有 73 分（「照英文词序逐句硬翻」）；
> 另有一份本地指标全绿的候选被模型判为 **32 分**（「六段里五段答非所问，严重错位」）——
> 这类错误任何统计都测不出来，只有读了台词才发现。

AI 仅负责**在候选之间排序**，不做绝对阈值判断。连接失败、超时或返回格式异常时
自动回退到本地排序，**不会影响字幕下载**。

### 两种检索方式，每个影视库各选一种

| 方式 | 适用范围 | 查询词 |
|---|---|---|
| **片名搜索** | 普通影视（电影 / 电视剧 / 动漫 / 综艺） | 电影：`片名 + 年份`；剧集：`剧名 + SxxExx` |
| **番号搜索** | 按番号命名的影片（如 `ABF-363`） | 从文件名提取的番号，并丢弃番号不符的候选 |

同一 Jellyfin 实例中可同时存在这两类内容：每个影视库各选一种，互不影响。

### 三类影片，三套语言策略

插件先判断影片属于哪一类，再决定「优先要哪种中文字幕」：

| 影片类型 | 判定方式 | 语言优先级 |
|---|---|---|
| 非中文影视 | 未配成番号库的库，默认按此处理 | 简英双语 → 纯简体 → 繁体 |
| 中文影视 | 同上，再看影片语种与产地 | 纯简体 → 纯繁体 → 双语 |
| 日本AV | **只有显式配置为「番号搜索」的库**才算 | 纯简体 → 纯繁体 → 双语 |

**只有番号库才会被当成日本AV** —— 普通影视库即使检索到带番号的候选名，
也不会套用 AV 的策略。英文、日文等非中文候选一律丢弃。

AI 提示词同样按类型分化，因为判断重点不同：非中文影视看译文是否自然、
中文影视查错别字、日本AV 识别低质量机翻。

**跨档择优**：非中文影视默认「有简英双语就用双语」，但如果纯简体 / 繁体版本的
AI 分数高出 8 分以上，会改用那份译文（可配置，填 0 表示无条件双语优先）。

### 每个影视库独立控制自动化

并非每个影视库都需要自动下载 —— 大部分影片本身已自带字幕。因此每个影视库提供三个独立选项：

- **检索方式**：番号搜索 / 片名搜索
- **自动补全**：是否由定时任务与实时入库自动为该库下载字幕
- **自动择优**：是否由「自动择优」任务重新比较该库已有的插件字幕

当所有影视库都未开启对应选项时，任务会直接跳过并记录一行日志，不会对全库执行无意义的扫描。

### 先预览，再决定

Jellyfin 的「搜索字幕」中，每条结果后附带两个按钮：

- **预览**（眼睛图标）：在弹窗中查看完整字幕，含时间轴、可切换自动换行，**不会写入影片目录**；
  确认合适后，点击弹窗中的「使用这份字幕」即可保存。
- **下载**（↓ 图标）：直接保存至影片目录。

预览的字幕全文仅保存在**服务器内存**中（30 分钟过期、最多 24 份、重启即清空），
任何情况下都不会写入磁盘。

### 搜索时可以加一句要求

手动「搜索字幕」的弹窗里有一个输入框，可以写这次想找什么样的字幕，
比如「要国配台本」「不要机翻」「尽量带片尾演职员表」。

它**不参与检索**（迅雷接口只认片名 / 番号），而是拼进本次 AI 评审的提示词，
让模型打分时把这些要求考虑进去。输入后自动保存，10 分钟未使用即过期。

### 不覆盖用户已有的字幕

- 网盘同步产生的 `<片名>.srt` / `<片名>.zh.srt`：**既不覆盖，也不删除**
- 视频内嵌字幕：默认视为「已有字幕」跳过，可在配置页打开
  **「含内嵌字幕的视频也补外挂字幕」**（适合内嵌是 PGS 图形字幕、或想换成能搜索能调样式的情况）
- 插件仅管理自身生成的 `<片名>.chi.<ext>`

## 两个计划任务

| 任务 | Key | 默认触发 | 作用 |
|---|---|---|---|
| 迅雷字幕 · 自动补全 | `ThunderSubtitleFill` | 每 6 小时 | 对开启了「自动补全」的影视库中**完全没有字幕**的条目，检索并下载最合适的字幕 |
| 迅雷字幕 · 自动择优 | `ThunderSubtitleRepick` | 每周日 04:00 | 对开启了「自动择优」的影视库中**已有插件字幕**的条目重新比较，仅在更优时替换 |

两个任务共用同一套检索 / 下载 / 过滤 / 排序 / 评审逻辑，与手动「搜索字幕」一致 ——
因此自动任务选中的候选，与弹窗中排在第 1 条的结果相同
（手动搜索时额外输入了附加提示词的情况除外，那会让模型按本次要求重新打分）。

### 实时补字幕

新条目入库并完成刮削后，插件会在 30 秒内为其补全一次字幕，无需等待定时任务：

- 每 30 秒查询一次「最近 6 小时入库且已完成刮削」的条目
- 仅处理这些新增条目，不扫描全库
- 仅处理开启了「自动补全」的影视库
- 定时任务保留作为补充机制（覆盖遗漏条目，或实时流程被全量任务占用时）

## 安装

### 方式 A：通过插件仓库（推荐，可自动更新）

控制台 → 插件 → 仓库 → 添加：

```
https://raw.githubusercontent.com/Louis-15/Jellyfin-Thunder-Subtitle/main/manifest.json
```

然后在「目录」中搜索 **Thunder Subtitle** 并安装，安装完成后重启 Jellyfin。
之后插件页面出现更新提示时点击「更新」即可升级，无需再手工传输文件。

### 方式 B：手工安装（服务器无法访问 GitHub 时）

请先备份插件目录；重启 Jellyfin 会造成数十秒不可用。

从 Release 页面下载 `thunder-subtitle_<version>.zip`，解压至 Jellyfin 配置目录下的
`plugins/ThunderSubtitle_<version>/`：

```bash
# 以 Docker 部署为例：将 /path/to/jellyfin/config 替换为映射给容器的配置目录
CONFIG=/path/to/jellyfin/config
VERSION=1.0.0.0
mkdir -p "$CONFIG/plugins/ThunderSubtitle_$VERSION"
unzip -o thunder-subtitle_$VERSION.zip -d "$CONFIG/plugins/ThunderSubtitle_$VERSION"
docker restart jellyfin   # 容器名请按实际情况填写

# 确认加载
docker logs --tail 200 jellyfin 2>&1 | grep -i "Thunder Subtitle"
```

- **Docker**：上述 `/path/to/jellyfin/config` 为**宿主机**上映射至容器 `/config` 的目录；
- **NAS（群晖 / 威联通 / UGREEN 等）**：无需 SSH，在 NAS 的文件管理器中将 zip 解压至映射出的
  `config/plugins/ThunderSubtitle_<version>/`，随后在容器管理界面重启 Jellyfin 即可。

插件目录内必须直接包含 `Jellyfin.Plugin.ThunderSubtitle.dll`、`meta.json` 与 `logo.png`，
不可多套一层文件夹，也不要放入 Jellyfin 自身的 dll（项目已设置 `CopyLocalLockFileAssemblies=false`）。

## 配置

控制台 → 插件 → Thunder Subtitle。

### 基本设置

只有一个「启用插件」开关：关闭后两个计划任务都不再下载任何字幕
（手动「搜索字幕」仍然可用，方便临时取一份）。

### 目标影视库

勾选需要本插件处理的影视库；每个库后有三个下拉框（未勾选的库同样显示当前设置）：

| 下拉框 | 取值 | 默认 | 说明 |
|---|---|---|---|
| 检索方式 | 番号搜索 / 片名搜索 | 片名搜索 | 番号库按 `ABF-363` 检索；普通影视库按片名 + 年份 / `S01E02` 检索 |
| 自动补全 | 是 / 否 | 否 | 定时任务与实时入库是否自动为该库下载字幕 |
| 自动择优 | 是 / 否 | 否 | 「自动择优」任务是否重新比较该库已有的 `.chi.*`；自动补全为「否」时该项隐藏 |

### 字幕下载与筛选

配置页按「插件处理一部影片的时间先后」排列，从上到下正好对应一次运行的时间线。

| 配置项 | 默认 | 说明 |
|---|---|---|
| 含内嵌字幕的视频也补外挂字幕 | 关 | 打开后，视频本身带内嵌字幕也会下载一份外挂中文字幕 |
| 单次上限 | 5 | 每次运行最多处理的条目数（仅统计实际发起检索的） |
| 最多候选数 | 25 | 每个条目最多下载多少份候选参与比较 |
| 请求间隔 | 500 ms | 两次**检索**之间的等待时间 |
| 下载并发数 | 4 | 同时下载的候选数量（1~8） |
| 单部影片下载预算 | 90 秒 | 到时后使用已下载的候选排序，不再等待响应缓慢的 CDN |
| 近似重复阈值 | 0.95 | 同一份字幕被不同站点转码改名后的合并阈值；填 1 关闭 |
| 每档评审份数 | 5 | 每种语言最多送几份给模型比较，总数不超过 12 |
| 超时 | 100 秒 | 超过后放弃 AI，按本地规则排序 |
| 片段数 | 6 | 送审时按时间轴取几段对齐片段 |
| 每段台词条数 | 8 | 非中文影视与日本AV 使用 |
| 中文影视每段条数 | 10 | 错别字是稀疏事件，抽样需要更密 |
| 日本AV 简体合格分 | 60 | 简体档低于此分且繁体更高时改用繁体；填 0 关闭 |
| 非中文影视跨档分差 | 8 | 纯简体 / 繁体高出首选档这么多分时改用该份；填 0 关闭 |
| 中文错别字告警 | 3 处/千字 | 只写日志提醒，不参与排序 |
| 缓存 AI 评分 | 开 | 「自动补全」与「自动择优」复用同一批判分 |
| 缓存有效期 | 30 天 | 换模型或改提示词后旧分数自动失效 |
| 日志级别 | 常规 | 错误 / 警告 / 常规 / 调试（逐条候选） |

早期版本的「优先语言」下拉框已废弃：语言优先级现在完全由影片类型决定，不需要手动选择。

## AI 评审

### 送审名单怎么定

仅按「台词最多」取前几名并不充分：条数最多的那批往往只是同一份机翻的不同转码，
真正的人工翻译会被排除在评审范围之外。现在的做法是：

1. **按影片类型分语言档位**（Tier 0 / 1 / 2，见上文「三类影片，三套语言策略」）；
2. **淘汰有硬伤的**：含中文条数不足 90%、未译标注超过 20 条、相邻台词最大空白超过 5 分钟、
   平均每条台词超过 10 秒。全部触线时退回全部候选 —— 一部冷门片只有机翻时，
   「从差的里面挑一份相对最好的」永远比「什么都不给」有用；
3. **近似去重**：同一份字幕被不同站点转码、改名、换标点后哈希不同，先合并再分配名额；
4. **排序**：缺陷数 → 条数偏离本批中位数的档位（每 5% 一档）→ 名字质量关键词（仅同分微调）；
5. **按档位分配名额**：每档取前 N 份（默认 5，上限 6），总数不超过 12；
   首选档凑不满时，余量让给其他档位。

由此，即使台词最多的那批全部是同一份机翻的副本，排在后面的干净纯中文台本仍能进入评审范围。

### 提交给模型的内容

- **按时间轴对齐的连续片段**，不是孤立单句：同一时刻的所有候选放在一起，
  模型才能判断「这句是不是联系上下文翻的」；
- 片段锚点覆盖片长的 12%～90%（默认 6 段 × 每段 8~10 条）；prompt 过长时自动缩减片段数，
  **绝不截断半句**；
- 附带**影片元数据卡**：片名、年份、类型、简介（截断 120 字），让模型按影片题材与年代评判用词；
- 要求模型为每份候选**引用一句原句**作为证据，插件在本地做子串核对 ——
  引不出或引错，说明它没真读文本；
- 模型返回 `{"candidates":[{"id":1,"score":85,"machine":false,"source":"human","evidence":"…","reason":"…"}]}`，
  插件仅用于重新排序。

三类影片的提示词不同：非中文影视重点看译文是否像中文（不拘泥字面、联系上下文、
符合影片题材与年代），中文影视重点查错别字，日本AV 重点识别低质量机翻。

成本参考：8 份候选约 2 万字符的 user prompt，一次评审约 75 秒。

### AI 接口

「AI 接口」是配置页里独立的一栏，与影片筛选参数分开：

| 配置项 | 说明 |
|---|---|
| 启用 AI | 关闭后只按本地规则排序，不调用任何接口 |
| 供应商 | **Open Code（内置）** 或自定义 OpenAI 兼容端点 |
| API Base URL | 仅「自定义」需要填写 |
| API Key | 以 `Authorization: Bearer` 发送，不写入日志 |
| 模型 | Open Code 可使用 `deepseek-v4.1-flash`、`glm-5.3-flash`、`kimi-k3` 等 |

**测试连接**按钮会先保存表单，再由服务器代发一条 `ping` 请求
（`POST /ThunderSubtitle/AiTest`），页面直接显示「连接成功 / HTTP 错误 / 超时」。
由服务器代发而不是浏览器直连，是因为 API Key 只存在服务器配置里，
第三方网关也几乎不会给 Jellyfin 页面放行 CORS。

### 供应商

**Open Code（内置）**

Base URL 固定为 `https://opencode.ai/inference/go/openai/v1`，无需填写。

按 [OpenCode Go 文档](https://opencode.ai/docs/go/) 的要求，每个请求都需携带稳定的会话 ID：

> Send a stable session ID in `x-opencode-session` for each conversation so we can
> optimize routing and prompt caching.

插件会自动附加该请求头，取值形如 `<本次运行 GUID>-<条目 ID>`，同一部影片在同一次运行内保持不变。
客户端使用插件自身的 User-Agent（`Jellyfin.Plugin.ThunderSubtitle/x.y.z`），文档同样要求不使用通用 SDK 名称。

**自定义（任意 OpenAI 兼容端点）**

填写自己的 Base URL 即可，此时不会发送 `x-opencode-session`。本地模型示例：

```
Base URL: http://127.0.0.1:11434/v1
模型名:   qwen2.5:14b
API Key:  （留空）
```

**隐私说明**：开启 AI 评审后，插件会将字幕抽样文本（部分对白）发送至所配置的服务端。
如对此有顾虑，可使用本地 Ollama / LM Studio，数据不会离开本机。

## 处理流程

1. **逐库枚举**：番号库检索 `Movie`，片名库检索 `Movie + Episode`
   （`CollapseBoxSetItems = false`，避免已加入合集的影片被隐藏）。
2. **生成查询词**：按该库配置的方式 —— 番号，或 `条目名 + 年份` / `剧名 + SxxExx`。
3. **检索**：请求迅雷字幕库。番号模式会以另一种前导零写法补充检索一次
   （索引将 `NIMA-086` 与 `NIMA-86` 视为两次不同的检索）；片名模式在无任何证据匹配时，
   退化为仅使用片名再次检索。
4. **下载并逐条校验**：
   - 解码：`utf-8-sig → utf-16(BOM) → utf-8 → gb18030 → big5 → shift_jis → windows-1252`，
     按 `汉字×3 - Latin1×2 - 异常字符×8` 打分选取最优编码；
   - 内容校验：必须为有效字幕文件（SRT 时间轴 / ASS `[Script Info]`+`Dialogue:` / `WEBVTT`），
     CDN 返回的错误页与 XML 将被丢弃；
   - 格式白名单 `srt / ass / ssa / vtt`，输出扩展名与内容一致（`.ass` 不会保存为 `.srt`）。
5. **语言过滤**：按影片类型保留可用的中文形式（简 / 繁 / 简英双语 / 繁英双语），
   英文、日文等非中文候选丢弃。该步骤必须位于排序之前 —— 英文每 KB 的字母数远高于中文，
   直接比较字符数会天然偏向英文。
6. **去重**：先精确去重（`md5(CRLF→LF 后的文本)`），再**近似去重**
   （3-gram Jaccard，默认阈值 0.95）—— 同一份字幕被不同站点改标点、改换行后哈希不同，
   精确去重拦不住，它们会一起挤进送审名额。
7. **健康度淘汰**：含中文条数不足 90%、未译标注超过 20 条、相邻台词最大空白超过 5 分钟、
   平均每条台词超过 10 秒，任一触发即淘汰；**全部触线时退回全部候选**，
   避免一部只有机翻的冷门片颗粒无收。
8. **排序**：
   - 番号模式先排除番号不符的候选（检索 `NIMA-86` 会返回 `NIMA-014`，其体积更大但属于其他影片）；
   - 片名模式先按**片名 / 季集 / 年份**证据分档，仅保留最强的一档，集数不符的候选直接丢弃；
   - 再按「语言档位」→「机翻标记数升序」→「**缺陷数**」→「**条数偏离本批中位数的档位**」
     →「名字质量关键词」（仅同分微调）→「条数」排列。
   - **台词字数不参与排序**：双语字幕夹着整行英文，字数天然翻倍，按字数排会把干净的
     纯中文台本挤出送审名单。
9. **AI 评审（可选）**：见上一节。
10. **写入**：`<片名>.chi.<ext>`，先写临时文件再原子替换，并删除其它扩展名的旧 `.chi.*`。
    已有 `.chi.*` 时仅在确有改进时才替换：语言档位更优直接换；机翻标记减少直接换
    （仅日本AV）；否则要求台词字符数多出 `max(30 字, 5%)`。
11. **刷新条目**：`ValidationOnly` + `ImageRefreshMode.None` —— 重新探测本地文件并挂载外挂字幕，
    但不会触发库设置中的 `SubtitleDownloadLanguages`，因此不会产生 `.chi.0.srt`。

## 安全边界

- 仅处理 `.chi.*`；网盘同步产生的 `<片名>.srt` / `<片名>.zh.srt` **永远不会被覆盖或删除**。
- 仅删除本插件命名的 `<片名>.chi.<ext>`（不含 Jellyfin 生成的 `<片名>.chi.0.srt` 冲突副本）。
- 下载仅允许 `*.xunlei.com` / `*.sandai.net` / `*.geilijiasu.com`，单文件上限 8 MB。
- 同一时间仅允许一个任务执行（信号量），自动补全与自动择优不会相互冲突。
- 幂等：内容相同直接跳过；**自动补全永远不会修改已有 `.chi.*`**，升级仅由「自动择优」完成。
- API Key 只保存在服务器插件配置里：不写进日志，也不下发到前端页面。
- 开启 AI 评审后，插件会把**字幕抽样片段**（部分对白）与影片元数据卡发送到所配置的服务端。
  不用 AI，或把「供应商」指向本地 Ollama / LM Studio，数据就不离开本机。
- 「测试连接」只发送一条 `ping`，不包含任何字幕内容或媒体库信息。

## 已知限制

- 番号搜索的影视库仅处理 `Movie`，且番号必须能从文件名识别；片名搜索的影视库同时处理 `Movie` 与 `Episode`。
- 片名搜索不具备番号那样的强制标识：中文片名检索出的候选常常以英文命名，此时无法核对片名，
  插件会按质量择优并在日志中告警，建议人工确认一次。
- **本地指标只能淘汰，不能排名**：含中文率、未译标注、大段空白、断句过粗这些都能量化，
  但「时间轴整体错位到别的情节上」只有读台词才发现 —— 实测有一份四项指标全绿的候选被模型判为 32 分。
  所以关闭 AI 评审时，插件只能保证「不选明显有毛病的」，无法保证「选到最好的」。
- AI 评审只看到 6 段抽样片段，仍有漏判可能；分数适合用于横向比较，不宜当作绝对标准。
- 番号不符的候选一律丢弃：宁可跳过，也不将其他影片的字幕写入当前影片。
- 刷新使用 `ValidationOnly`，不会重新拉取远程元数据；`.strm` 指向的远程视频本身不会被探测。
- 上游无候选时不会回退到其他字幕站点。
